01진입점이 세 개다

이 폴더를 처음 열면 "어디서부터 읽어야 하나"가 막막하다. 진입점이 하나가 아니라 셋이고, 서로 층이 다르기 때문이다. 이 셋을 구분하는 것이 출발점이다.

층파일누가 부르는가무엇을 하는가
프로세스server/flow/run-application.sh농협 플랫폼환경변수를 세팅하고 Gunicorn을 띄운다
HTTPapp_custom_parser/main.pyKnowledge Lake/parsing, /parsing/result/{uuid}, /health를 제공한다
업무 로직service/parsing_service.py의 parse()main.py가 띄운 별도 프로세스실제 파싱을 하고 결과 파일을 만든다

중요한 오해 하나를 먼저 풀어야 한다. 우리가 농협 외부에 서버를 세워 두고 URL을 알려주는 방식이 아니다. 우리는 소스코드를 등록하고, 농협 플랫폼이 그 소스로 서버 프로세스를 띄운다. 그렇게 뜬 서버를 KL이 호출한다. 그래서 등록하는 소스 안에 FastAPI 앱과 Gunicorn 실행 스크립트가 함께 들어 있는 것이다.

세 층 중 우리가 실제로 작성해야 하는 곳은 세 번째 하나뿐이다. 앞의 둘은 농협이 이미 만들어 줬고 그대로 유지하는 것이 원칙이다.

02폴더 지도

원본 예제와 현재 구현을 겹쳐 놓은 지도다. 색이 다른 줄이 우리가 추가한 것이다.

# 농협 원본 예제 (1.awx_custom_parser_example_api)
readme.md                     ← HRC 출력 규격의 규범. 6장에서 쓴다
out_sample_hrc.jsonl          ← 결과 본문 예시
out_sample_hrc.json           ← 결과 INFO 예시
server/flow/
├─ readme/parser_howto.txt     ← KL 호출 계약. 가장 중요한 문서
├─ run-application.sh          ← 프로세스 진입점
├─ setup-application.sh        ← wheel 설치
├─ test-application.sh         ← 스모크 테스트
├─ whl/                        ← 폐쇄망용 wheel
└─ app_custom_parser/
   ├─ main.py                  ← HTTP 진입점
   ├─ gunicorn_config.py       ← worker·포트 설정
   └─ service/parsing_service.py ← 여기 parse() 안을 채우는 게 우리 일

# 현재 구현 (repo-analysis/custom-parser) — 위 구조를 그대로 유지하고 아래를 추가
server/flow/app_custom_parser/service/
   ├─ parsing_service.py        ← parse() 가 아래 모듈들을 조립한다
   ├─ config.py                 ← ETL 접속값을 option·환경변수에서 해석
   ├─ etl_client.py             ← ETL API 4개 호출. 표준 라이브러리만 씀
   ├─ etl_adapter.py            ← ETL 응답 → 내부 모델로 정규화·검증
   ├─ document_model.py         ← 내부 모델 정의 (Page, Region)
   ├─ hrc_exporter.py           ← 내부 모델 → HRC 두 파일
   ├─ result_contract.py        ← 결과 파일이 규격에 맞는지 최종 검사
   └─ status.py                 ← 실행에 안 쓰임. 테스트만 import

모듈이 여섯 개로 늘어난 이유는 단순하다. parse() 하나에 ETL 호출과 JSON 검증과 HRC 변환을 전부 넣으면 읽을 수 없고, ETL 응답이 가이드와 다를 때 고칠 범위가 커진다. 바깥에서 보이는 함수는 여전히 parse() 하나이고 나머지는 그 안에서만 쓰인다. 플랫폼과의 계약은 바뀌지 않았다.

읽는 순서를 추천하면 이렇다. main.py → parsing_service.py → etl_client.py → etl_adapter.py → hrc_exporter.py. 앞의 둘만 읽어도 전체 뼈대는 잡힌다.

03서버가 뜨기까지

run-application.sh는 짧지만 뒤에서 벌어지는 일을 전부 결정한다. 네 덩어리로 나눠 읽으면 된다.

  1. 앱 이름을 고정한다 run-application.sh:5

    FLOW_APP_NAME="app_custom_parser". 이 이름이 나중에 cd 대상이 되므로 디렉터리 이름과 반드시 같아야 한다.

  2. 실행 환경을 판별한다 :10-20

    /infer-model 디렉터리가 있으면 농협 추론 환경, 없으면 로컬 예제 환경으로 보고 PATH_SOURCE와 PATH_TEMP를 다르게 잡는다. PATH_TEMP가 핵심이다. 모든 작업 디렉터리가 이 밑에 생기고, main.py:23이 이 값을 PATH_WORK로 읽는다.

  3. 앱 디렉터리로 이동한다 :39-45

    cd $PATH_SOURCE/$FLOW_APP_NAME. 이 한 줄 때문에 프로세스의 작업 디렉터리가 app_custom_parser/가 된다. 4장에서 이게 왜 중요한지 나온다.

  4. Gunicorn을 띄운다 :62-64

    PYTHONPATH에 custom_libs를 더하고 gunicorn main:app --config gunicorn_config.py를 실행한다. main:app은 "main.py에서 app 객체를 가져와 실행하라"는 뜻이다. main.py:25의 app = FastAPI()가 바로 그 객체다.

gunicorn_config.py에서 실제로 알아야 할 값은 셋이다. 포트는 MLDL_PROBE_PORT이고 기본값이 9101이다(:8, :33). worker는 일반 환경 2개, 농협 추론 환경 8개다(:30, :38). dlp.is_infer_env()로 환경을 구분하는데(:37), 이 dlp 모듈은 농협 플랫폼 이미지에만 있어서 로컬에서는 이 파일을 import할 수 없다.

worker가 여러 개라는 사실은 그냥 넘기면 안 된다. POST를 받은 worker와 GET을 받는 worker가 다를 수 있다. 그래서 작업 상태를 메모리가 아니라 파일에 적는다. 다음 장의 핵심이다.

04요청 한 건의 생애

이 구조에서 가장 헷갈리는 부분이다. 웹 요청을 처리하는 프로세스와 실제 파싱을 하는 프로세스가 서로 다르고, 직접 대화하지 않는다. 둘은 디스크에 놓인 상태 파일 하나로만 소통한다.

① ~ ④ 접수 단계 main.py:28-116

KL이 src_file과 option을 multipart로 보낸다. option은 Base64로 인코딩된 JSON 문자열이다. main.py:69-73이 이걸 풀어 딕셔너리로 만든다.

그다음 uuid4().hex로 32자리 ID를 만들고(:81), PATH_TEMP/<uuid>/image까지 한 번에 생성한 뒤(:84-86) 원본 파일을 그 안에 저장한다(:89-91). 상태를 PARSING으로 적고(:93) 백그라운드 작업을 등록한 다음(:98), 파싱이 끝나기를 기다리지 않고 곧바로 202를 돌려준다(:105-116).

{"result": "OK", "body": {"uuid": "a1b2…", "timeout": 600}}

여기서 나오는 uuid는 KL이 우리 작업을 다시 조회하기 위한 키다. ETL의 task_id와는 아무 관계가 없다. 두 ID를 섞지 않는 것이 중요하다.

③ 서브프로세스가 뜨는 방식 main.py:241-243

이 부분이 처음 보면 가장 낯설다. 함수를 직접 호출하지 않고 문자열로 파이썬 코드를 조립해 새 프로세스를 띄운다.

python -c "from service.parsing_service import parse; parse('…/temp/ab12/','…/temp/ab12/image','…/광고.pdf',{'etl': {…}})"

인자는 repr()로 파이썬 리터럴 문자열로 바뀐다. 딕셔너리도 그대로 들어간다. 이 명령이 동작하는 이유는 3장의 cd 때문이다. 프로세스의 작업 디렉터리가 app_custom_parser/이고 python -c는 작업 디렉터리를 모듈 검색 경로에 넣으므로, service 패키지가 보인다.

왜 이렇게 하느냐면, 파싱이 오래 걸리거나 죽어도 웹 worker가 함께 죽지 않게 하려는 것이다. 타임아웃이 지나면 :251-258이 프로세스를 죽이고 작업 디렉터리를 지운다.

작업 디렉터리에 파일이 쌓이는 순서

실제로 실행해 확인한 결과다. 자주색이 그 단계에서 새로 생긴 파일이다.

① 원본 저장 직후

  • 광고.pdf
  • image/

② PARSING 기록

  • 광고.pdf
  • image/
  • genaikl.status

③ HRC 생성 후

  • 광고.pdf
  • image/
  • genaikl.status
  • 광고.pdf_hrc.jsonl
  • 광고.pdf_hrc.json

④ DONE 기록

  • 광고.pdf
  • image/
  • genaikl.status
  • 광고.pdf_hrc.jsonl
  • 광고.pdf_hrc.json

genaikl.status의 내용은 이렇게 단순하다.

{"status": "PARSING", "message": ""}     ← 작업 중
{"status": "DONE", "message": ""}        ← 성공
{"status": "ERROR", "message": "사유"}   ← 실패

쓸 때는 .tmp에 먼저 쓰고 shutil.move로 바꿔치기한다 (parsing_service.py:20-26). 웹 worker가 반쯤 쓰인 파일을 읽는 일을 막기 위해서다.

⑤ ~ ⑥ 결과 조회 단계 main.py:131-238

KL은 받은 uuid로 GET /parsing/result/{uuid}를 반복 호출한다. main.py는 상태 파일을 읽어 세 가지로 나눠 답한다.

상태응답위치
PARSING200 + {"status":"PARSING"}:203-205
ERROR200 + {"status":"ERROR","message":…}:206-212
DONE200 + 결과 ZIP:144-202
디렉터리 없음500 + {"message":"Requested url does not exist."}:221-223

DONE일 때 하는 일은 작업 디렉터리를 훑어 허용된 접미사를 가진 파일만 골라 담는 것이다(:152-163). _hrc.jsonl, _hrc.json, doc_data.json이 그 목록이고, image/에 파일이 있을 때만 _img.zip을 만들어 추가한다(:167-182). 원본 파일과 상태 파일은 목록에 걸리지 않으므로 자동으로 빠진다.

ZIP을 만들고 나면 작업 디렉터리를 통째로 지운다(:193-195). 그래서 같은 uuid로 두 번 조회하면 두 번째는 500이 돌아온다. 결과를 한 번만 가져갈 수 있다는 뜻이니 기억해 둘 것.

05parse() 안에서 일어나는 일

여기서부터가 우리가 쓴 코드다. parsing_service.py:61-68의 parse()는 놀랄 만큼 짧다.

def parse(work_dir, img_dir, file_path, option=None):
    try:
        write_parse_status(work_dir, "PARSING")
        process_document(work_dir, img_dir, file_path, option)
        write_parse_status(work_dir, "DONE")
    except Exception as exc:
        write_parse_status(work_dir, "ERROR", str(exc))

계약은 이 모양이 전부다. 무엇을 하든 마지막에 DONE 또는 ERROR를 반드시 남긴다. 남기지 않으면 KL이 영원히 PARSING만 보게 된다. 실제 작업은 process_document()(:40-58)가 다섯 줄로 조립한다.

  1. 설정을 만든다 config.py:71

    EtlConfig.from_sources(options)가 ETL 접속 주소와 author, ws_id를 찾는다. 찾는 순서는 option["etl"] → option["parser_info"]["prop"] → 환경변수다. 셋 다 없으면 여기서 예외가 난다.

  2. ETL을 호출한다 etl_client.py:270-276

    analyze()가 아래 그림의 네 단계를 순서대로 수행하고 Default JSON을 돌려준다.

  3. 내부 모델로 바꾼다 etl_adapter.py:113

    convert_default_json()이 ETL 응답을 검증하면서 Page와 Region 목록으로 정규화한다. 여기서 형식이 어긋나면 예외를 낸다.

  4. HRC 두 파일을 쓴다 hrc_exporter.py:94

    export_hrc()가 광고.pdf_hrc.jsonl과 광고.pdf_hrc.json을 만든다.

  5. 규격을 최종 검사한다 result_contract.py:13

    collect_result_files()가 파일이 제대로 만들어졌는지 다시 읽어 확인한다. 여기서 실패하면 DONE 대신 ERROR가 된다.

세 API의 쿼리 파라미터 이름이 file_path → docPath → docResultPath로 계속 바뀐다. 오타가 아니라 ETL 가이드 원문이 실제로 그렇게 되어 있다(가이드 p.32, p.34, p.36). 고치면 안 된다.

06결과 파일 두 개

이름이 비슷해서 헷갈리는데 역할이 완전히 다르다. 확장자 하나 차이다.

광고.pdf_hrc.jsonl광고.pdf_hrc.json
무엇문서 본문문서 정보
형식줄마다 독립적인 JSON 객체 하나전체가 JSON 객체 하나
쓰임VectorDB에 적재되어 검색된다파일명·크기·페이지 정보를 전달한다
만드는 곳hrc_exporter.py:107-141

파일명 규칙에 함정이 있다. 원본파일명에 확장자가 포함된다. 광고.pdf가 들어오면 광고_hrc.jsonl이 아니라 광고.pdf_hrc.jsonl이다. 원본 readme.md:21-22와 샘플 코드가 모두 src_file.filename + "_hrc.jsonl" 형식이다.

본문 파일의 생김새

{"item":"h1","value":"상품 안내"}
{"item":"text","value":"최저 연 3.5%","page":1}
{"item":"table","value":"<table>…</table>","page":1,"type_property":{"title":""}}

쓸 수 있는 item은 text, table, image, h1~h4 일곱 가지뿐이다(readme.md:166). value는 필수다. h1~h4는 단순 텍스트가 아니라 뒤따르는 본문에 붙는 계층 메타데이터로 쓰인다. 위 예에서 "최저 연 3.5%"는 KL에 적재될 때 "상품 안내" 아래에 속한 문장이 된다.

변환 규칙은 hrc_exporter.py:28-33 한 함수에 다 들어 있다. ETL의 Table은 table로, Title이면서 section_level이 1~4면 h1~h4로, 나머지는 전부 text다. 그래서 지금은 Figure도 이미지가 아니라 텍스트가 된다.

정보 파일의 생김새

{"name":"광고.pdf","source":"…","file_type":"pdf","size":68475,
 "title":"상품 안내","subject":"","updated":"","parsed_status":"S",
 "page_info":[{"page":1,"width":1275,"height":1650}]}

page_info의 width와 height는 아직 확정되지 않은 값이다. ETL이 준 숫자를 그대로 넣고 있는데, 농협 샘플은 같은 자리에 21.0×29.7(cm)이나 595.3×841.9(PDF point)를 쓴다. 실제 등록 결과로 단위를 확인해야 한다.

07처음 읽을 때 걸리는 것들

같은 이름의 함수가 두 번 정의되어 있는데 괜찮은가?

main.py:32와 :135가 둘 다 parsing_text_docx_to_json이다. 파이썬에서는 뒤의 것이 앞의 것을 덮지만, FastAPI는 데코레이터를 만나는 순간 이미 라우트를 등록하므로 두 엔드포인트 모두 정상 동작한다. 원본 예제 그대로이고 읽기에 나쁠 뿐 버그는 아니다.

service.parsing_service를 import하는데 service 폴더가 어디 있다고?

main.py와 service/가 같은 디렉터리에 있고, 3장에서 본 cd $PATH_SOURCE/$FLOW_APP_NAME 때문에 프로세스 작업 디렉터리가 바로 그곳이다. 파이썬은 작업 디렉터리를 모듈 검색 경로에 넣으므로 service가 보인다. 폴더를 평평하게 펴면 이 import가 깨진다는 뜻이기도 하다.

UUID가 두 종류인가?

그렇다. main.py:81이 만드는 32자리 UUID는 KL이 우리를 조회하는 키이고, ETL이 주는 task_id와 file_path는 우리가 ETL을 조회하는 키다. 이름이 비슷해 섞기 쉬운데 서로 아무 관계가 없다.

스모크 테스트를 돌렸는데 ERROR만 나온다.

test-application.sh는 option=e30=을 보낸다. 이건 빈 JSON {}다. ETL 접속값이 환경변수에도 없으면 config.py에서 Missing ETL configuration 예외가 나고 그대로 ERROR가 된다. 원본 예제는 하드코딩 샘플을 쓰기 때문에 같은 조건에서도 ZIP이 나왔다. 현재 구현은 ETL 값 없이는 끝까지 갈 수 없다.

img_dir 인자를 받는데 코드에서 안 쓰는 것 같다.

맞다. parsing_service.py:47이 del img_dir로 버린다. 지금은 이미지를 만들지 않기 때문이다. ETL Default JSON에는 이미지 파일 경로 필드가 아예 없어서 텍스트만 얻을 수 있다. 나중에 이미지를 붙이려면 별도 설계가 필요하다.

status.py는 언제 쓰이나?

실행 중에는 안 쓰인다. main.py:19는 parsing_service의 함수를 가져다 쓰고, status.py는 테스트에서만 import된다. 같은 일을 하는 코드가 두 벌 있는 셈이라 정리 대상이다.

원본 예제를 왜 그대로 안 쓰고 고쳤나?

세 가지가 실제로 동작하지 않았다. option이 multipart가 아니라 query 파라미터로 선언돼 KL이 보내는 값을 받지 못했고, Base64 디코딩이 주석 처리된 채 options = {}로 덮어써져 있었으며, 이미지가 없어도 빈 ZIP을 항상 만들어 넣었다. 그 외의 골격은 건드리지 않았다.

08직접 돌려 보기

농협 환경이 없어도 핵심 모듈은 외부 패키지 없이 확인할 수 있다. Python 3.11 기준이다.

테스트부터

cd repo-analysis/custom-parser
python -m unittest discover -s tests -v

FastAPI가 없으면 계약 테스트 5개는 건너뛰고 10개만 돈다. 전부 돌리려면 fastapi와 httpx가 필요하다.

변환기만 따로 돌려 보기

ETL 없이 Default JSON 픽스처로 HRC를 만들어 보는 것이 구조를 이해하는 데 가장 빠르다.

cd server/flow/app_custom_parser
python - <<'EOF'
import sys, os, json, tempfile
sys.path.insert(0, os.getcwd())
from service.etl_adapter import convert_default_json
from service.hrc_exporter import document_to_hrc_items
from pathlib import Path

payload = json.loads(Path("../../../tests/fixtures/default_result.json").read_text(encoding="utf-8"))
doc = convert_default_json(payload)
for item in document_to_hrc_items(doc):
    print(json.dumps(item, ensure_ascii=False))
EOF

출력이 이렇게 나온다. ETL의 Figure가 text로 바뀌는 것을 직접 볼 수 있다.

{"item":"h1","value":"상품 안내"}
{"item":"text","value":"최저 연 3.5%","page":1}
{"item":"table","value":"<table>…</table>","page":1,"type_property":{"title":""}}
{"item":"text","value":"이미지 내부 문구","page":1}   ← 원래 Figure 였다

픽스처를 바꿔 가며 실험해 볼 것

  • Title에서 section_level을 지우면 h1이 아니라 text가 된다. 헤딩 판정이 이 필드에만 의존한다는 걸 확인할 수 있다.
  • 모든 contents를 빈 문자열로 만들면 예외가 난다. 텍스트가 하나도 없는 문서는 결과를 만들지 못하고 ERROR가 된다는 뜻이다.
  • pages 키를 지우면 etl_adapter.py:57에서 스키마 오류가 난다. ETL 응답을 검증 없이 믿지 않는다는 것을 볼 수 있다.

구조를 파악했으면 같은 docs/ 폴더의 문서로 넘어가면 된다. 01은 원본 예제 분석, 02는 ETL API 상세, 03은 통합 구조, 04는 검증 체크리스트다. 원본 예제와의 차이를 항목별로 대조한 감사 결과는 별도 보고서에 있다.
